Demo Spec — 2026-08-31

OnAir Console

楽天市場の出店店舗が、自店のShoplive Sellerを起点に自由にライブコマース配信を行うための、楽天専用ダッシュボード設計書。

対象: 店舗用画面 / 楽天市場管理者用画面 接続: Shoplive API v2（実接続） 版: Demo v0.1

01概要とスコープ

審査や在庫連携、決済といった楽天側の業務ロジックはこのデモの本題ではない。本題は、Shopliveという配信基盤の上に、楽天の店舗運営フローをどう重ねるかという設計そのものだ。

本デモは、楽天市場の出店店舗がShopliveのアカウントを直接意識することなく、「楽天の画面から申請し、楽天の画面でライブを作り、楽天の画面で配信する」という体験を提供することを目的とする。裏側では実際にShoplive API（https://private.shopliveapi.com/v2/…）へリクエストが飛び、Seller・Campaign・商品の作成やライブ配信の開始/終了が本物のAPIレスポンスとして返ってくる。

すでにJWT／AccessKeyによる認証と Retrieve a campaign info の疎通確認は完了している（存在しないcampaignKeyに対して 404 / -710 Campaign does not exist が返り、401ではないことから認証が正しく通っていることを確認済み）。

デモにおける実装/モックの切り分け

実際にAPI接続する部分：Seller作成、Campaign作成・更新・商品紐付け、配信開始/終了、在庫状況・Now表示の切り替え、統計取得——つまり「Shopliveが本来やること」はすべて本物のAPIを叩く。モックで済ませる部分：店舗申請・ライブ申請の審査ステータス管理、店舗↔SellerIdの対応表など、Shoplive自体には存在しない「楽天独自の業務データ」はブラウザ内で完結させる（詳細は実装方針）。

02全体アーキテクチャ

店舗UIと管理者UIはいずれもブラウザで完結するフロントエンド中心の構成とし、Shoplive本番APIへの通信だけをサーバー側の薄いプロキシに集約する。理由は単純で、AccessKeyとJWTをブラウザのJavaScriptに直接埋め込むと誰でも閲覧できてしまうため、秘密鍵の保持場所をサーバー環境変数（.env）1箇所に限定する。

コンポーネント

  • 店舗コンソール — 店舗が複数Sellerを切り替えながらライブの作成・設定・配信を行う画面群。
  • 管理者コンソール — 楽天市場運営者が店舗申請とライブ申請を審査し、オンエア中の配信を監視する画面群。
  • ローカルモックストア — Shopliveには存在しない「審査中/却下」といった楽天独自ステータスを保持する、DBを持たない簡易ストア。
  • Next.js APIプロキシ — Authorization: Bearer ヘッダーの付与だけを行う薄い中継層。ビジネスロジックは持たない。

03データモデル

Shoplive側のSeller・Campaign・Productは、Sellerを中心にゆるく紐づくハブ&スポーク構造である。Productは特定のCampaignに属さず、Add/Removeの都度キャンペーンに紐付け・解除される中間関係にある。

オブジェクト所有元キー備考
Seller楽天店舗 1件に対応sellerId店舗名・店舗URL・説明のみを持つ薄いマスタ
Campaignライブ 1本に対応campaignKeySeller・商品リストを任意で参照。ステータスは READY/REHEARSAL/ONAIR/ENDED
ProductSellerの商品マスタproductId複数Campaignで再利用可能。Campaignごとの並び順・在庫状態はCampaignProduct側で管理

これに対し、楽天独自に必要となるのは「審査」という概念そのものだ。Shopliveには承認待ちの状態がないため、以下2つのエンティティをローカルモックストアに追加する。

// ローカルモックストア（localStorage）のスキーマ
type StoreApplication = {
  id: string
  storeName: string          // 店舗名
  storeUrl: string           // 店舗URL
  liveOverview: string       // ライブ配信の概要
  status: "審査中" | "承認" | "却下"
  shopliveSellerId?: number  // 承認時にCreate a sellerで採番
  createdAt: string
}

type LiveApplication = {
  id: string
  storeApplicationId: string
  title: string
  scheduledStartAt: string
  productIds: number[]
  status: "審査中" | "承認" | "却下"
  campaignKey?: string       // 申請と同時にCreate a campaignで採番
  createdAt: string
}

04承認ワークフロー

審査時にはタイトル・サムネイル・登録商品まで確定している必要があるため、ライブ申請は送信した瞬間に本物のCampaignをShoplive上に作成する。ただし所属Sellerは楽天が管理する「審査待ちプレースホルダーSeller」とし、内容が公開状態に見えないようにしておく。管理者が承認した時点で、はじめて該当店舗の実SellerへtransferToSellerする。

店舗の新規アカウント申請も同じ考え方に揃える。申請内容（店舗名・店舗URL・概要）はまずローカルに「審査中」として保存し、管理者が承認した瞬間に Create a seller を呼んで初めてShoplive上にSellerが生まれる。Sellerは作成後すぐに使える状態のため、Campaignのようにプレースホルダーを挟む必要はない。

05画面設計 & APIマッピング

各画面が呼び出すShoplive APIと、ローカルモックストアが受け持つ範囲を明示する。実API は本物のShopliveエンドポイントへの通信、ローカル は楽天独自データの読み書きを示す。

CampaignMetaの全項目とAPI対応状況

「ライブの新規作成」「ライブの設定」画面はCreate/Update a campaignが受け付ける項目を漏れなく網羅する。逆に、Campaignオブジェクトが持つがCreate/Update APIのリクエストボディには存在しない項目（画像・動画・タグ）も明示し、対象外であることを設計上はっきりさせる。

項目API対応画面備考
titleCreate/UpdateS-3, S-4必須。空文字での更新不可（-837）
descriptionCreate/UpdateS-3, S-4任意の説明文
scheduledStartAtCreate/UpdateS-3, S-4UTC ISO形式。配信予定日時
scheduledEndAtCreate/UpdateS-3, S-4任意。配信終了予定日時
rehearsalPasscodeCreate/UpdateS-3, S-4リハーサル入室用パスコード
serveReplayCreate/UpdateS-3, S-4終了後にリプレイを公開するかの真偽値
seller.sellerIdCreateのみS-3 / A-3Update不可。所属変更はtransferToSeller専用APIで行う（承認ワークフロー）
brand.brandIdCreate/Updateで受理対象外Brandを作成・検索するAPIが存在せず、Shoplive管理コンソール側で用意されたIDが必要。本デモでは未使用
tagsAPI非対応対象外Campaignオブジェクトのレスポンスには含まれるが、Create/Updateのリクエストボディには存在しない
logoImageUrl / preCampaignVideoUrl / preCampaignImageUrl / postCampaignImageUrl / backgroundImageUrl / ieUnsupportImageUrlAPI非対応対象外いずれもレスポンス専用。ポップアップと同様、Shoplive管理コンソールでのみ設定可能
campaignId / campaignKey / accessKey / shoplivePlayerUrl / campaignStatus / userCount / likeCount / campaignStartedAt / campaignEndedAt / createdAt / updatedAt読み取り専用S-2, S-5システムが自動採番・更新。表示のみで編集不可
店舗用画面

S-1新規アカウント作成画面

店舗名・店舗URL・ライブ配信の概要を入力し、楽天市場管理者の審査に申請する。

UI要素
店舗名/店舗URL/概要フォーム、送信後は「審査中」ステータス表示
API
ローカルのみ StoreApplicationを status=審査中 で作成。この時点ではShopliveは未呼び出し

S-2ライブ一覧画面

自店（複数Seller切り替え可）が持つライブを、審査中・配信前・配信中・終了で横断表示する。

UI要素
Sellerスイッチャー、ステータス別タブ、サムネイル付きカード一覧
API
  • 実API GET /campaign?sellerId={id}（Search campaigns、承認済みライブ）
  • ローカル LiveApplication（審査中/却下）をマージして表示

S-3ライブの新規作成画面

Create a campaignが受け付ける項目（タイトル・説明・配信開始/終了予定・リハーサルパスコード・リプレイ公開可否）と登録商品を確定させ、審査に申請する。

UI要素
基本情報フォーム（タイトル/説明/配信開始日時/配信終了予定日時/リハーサルパスコード/リプレイ公開トグル）、サムネイル画像（Rakuten一覧表示用のローカル項目でShopliveへは送信しない）、商品ピッカー、プレビュー
API
  • 実API POST /campaign（title / description / scheduledStartAt / scheduledEndAt / rehearsalPasscode / serveReplay、seller=プレースホルダー）
  • 実API POST /campaign/{campaignKey}/product（商品一括紐付け）
  • ローカル LiveApplicationを status=審査中 で作成、campaignKeyとサムネイル画像を保存

S-4ライブの設定画面

承認済みライブのCampaignMeta全項目（タイトル・説明・配信開始/終了予定・リハーサルパスコード・リプレイ公開可否）・商品構成・表示順を編集する（審査中は取り下げのみ許可）。ポップアップ（バナー）・画像/動画系項目はAPI非対応のため本画面の対象外（制約参照）。

UI要素
基本情報タブ（タイトル/説明/配信開始・終了日時/リハーサルパスコード/リプレイ公開トグル）、商品構成タブ（追加/削除/並び替えUI、ドラッグ操作）
API
  • 実API PUT /campaign/{campaignKey}（Update a campaign）
  • 実API POST / DELETE /campaign/{campaignKey}/product
  • 実API PUT /campaign/{campaignKey}/product/order

S-5ライブ配信中コンソール画面

実際の配信操作を行う、店舗にとって最も緊張感のある画面。

UI要素
開始/終了ボタン、商品ごとの在庫状況・Now表示トグル、簡易視聴統計
API
  • 実API POST /console/{campaignKey}/start?rehearsal=
  • 実API POST /console/{campaignKey}/end
  • 実API PUT /console/{campaignKey}/product/stockStatus
  • 実API PUT /console/{campaignKey}/product/show（リアルタイム反映）
  • 実API GET /campaign/{campaignKey}/stats
楽天市場管理者用画面

A-1アカウント申請一覧・承認却下画面

店舗からの出店（Seller化）申請を審査する。

UI要素
申請一覧テーブル、店舗詳細ドロワー、承認/却下ボタン
API
  • ローカル StoreApplication（status=審査中）を一覧取得
  • 実API 承認時 POST /seller（Create a seller）→ sellerIdをローカルに保存

A-2オンエア中のライブ一覧画面（プレビュー付き）

現在配信中のライブを一望し、プレビューでそのまま内容確認できる監視画面。

UI要素
配信中カードのグリッド、クリックでプレビュー動画埋め込み、簡易視聴数
API
  • 実API GET /campaign?campaignStatus=ONAIR（Search campaigns）
  • 実API 各カードで stream.previewLiveUrl を埋め込み再生
  • 実API GET /campaign/{campaignKey}/stats（任意、視聴数の補助表示）

A-3新規ライブ申請一覧・承認却下画面

店舗が申請したライブの内容をリハーサルプレビューで確認し、公開可否を判断する。

UI要素
申請一覧テーブル、リハーサルプレビュー、承認/却下ボタン
API
  • ローカル LiveApplication（status=審査中）を一覧取得
  • 実API 承認時 PUT /campaign/{campaignKey}/transferToSeller/{sellerId}
  • ローカル 却下時は status=却下 のみ更新（Shoplive側は残置）

06実装方針

「フロントエンド中心・モック中心」という方針に沿って、次の構成を採る。

  • Next.js（App Router）で店舗/管理者の両UIを1アプリに同居させ、画面右上のロールスイッチで切り替える（デモのため実認証は行わない）。
  • Route Handler（/app/api/shoplive/*）を薄いプロキシとして用意し、.envのAccessKey/JWTを付与してShopliveへ中継するだけの役割に限定する。ビジネスロジックは持たせない。
  • 楽天独自データ（StoreApplication / LiveApplication）はDBを持たずlocalStorageで完結させる。リロードで消えることはデモとして許容する。
  • 楽天管理用プレースホルダーSellerを1件、デモ開始前に手動で作成しておき、そのsellerIdを設定値として保持する。

07制約と注意点

  • 楽天独自データはブラウザのlocalStorageに閉じるため、別端末・別ブラウザ間で状態は共有されない。デモは同一ブラウザ内で完結させる。
  • 却下されたライブ申請のCampaignをShoplive側でどう扱うか（残置 or 削除）は運用ルール次第。デモでは残置とし、削除は任意対応とする。
  • 本デモの.envに格納したAccessKey/JWTは単一のShopliveアカウントを指す。複数店舗（Seller）はすべてこの1アカウント配下で管理される前提。
  • チャット管理・ポップアップ管理などShoplive管理コンソール側の高度な運用機能は、デモの主要導線（作成〜配信）には含めない。
  • ポップアップ（バナー）登録はAPI非対応。Shoplive API v2にはポップアップ関連のエンドポイントが存在せず、ガイド上も「Shoplive管理コンソールのボタン操作」としてのみ説明されている。そのため本デモの「ライブの設定」画面では扱わず、対象外とする。将来的にAPI提供の要望をShoplive側（ask@shoplive.cloud）へ出すことは可能。
  • キャンペーンの画像・動画系項目（logoImageUrl / preCampaignVideoUrl / preCampaignImageUrl / postCampaignImageUrl / backgroundImageUrl / ieUnsupportImageUrl）とtagsもAPI非対応。Campaignオブジェクトのレスポンスには含まれるが、Create/Update a campaignのリクエストボディでは受け付けられない。ポップアップと同じくShoplive管理コンソール側の設定項目であり、本デモの「ライブの新規作成」画面にあるサムネイル項目はAPIには送信されないRakuten一覧表示専用のローカル項目として扱う。
  • brand.brandIdはCreate/Updateのリクエストとしては受理されるが、Brand自体を作成・検索するAPIが存在しない。事前にShoplive管理コンソール側で用意されたIDを渡す運用が必要になるため、本デモでは未使用とする。

08拡張の方向性

  • 楽天IDとの実認証連携（SSO）、店舗ロールベースのアクセス制御
  • ローカルモックストアを実DBへ置き換え、複数運用者・複数端末での状態共有
  • Shoplive Webhookを受けて配信状況をリアルタイム同期（オンエア一覧のポーリング撤廃）
  • 審査却下時のCampaign自動削除、通知（承認/却下）のメール連携
